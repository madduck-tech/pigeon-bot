# Процесс разработки

Документ определяет обязательный путь задачи от идеи или бага до релиза. Правила работы с кодом находятся в [CLAUDE.md](../CLAUDE.md), эксплуатация — в [operations.md](operations.md).

## Роли

- **Product Owner** — пользователь, взаимодействующий с агентом. Определяет продуктовые цели и приоритеты, принимает продуктовые требования, компромиссы и ADR, затрагивающие продукт.
- **Исполнитель** — агент или разработчик. Анализирует задачу, готовит решение, реализует его, обновляет документацию и предоставляет доказательства проверки.
- **Критик** — независимый агент с навыком `gopnik-critic`. Пытается опровергнуть постановку, диагноз и другие опорные утверждения. Не принимает продуктовых решений.
- **Проверяющий** — независимый агент с навыком `gopnik`. Пытается сломать готовое изменение и выносит вердикт по конкретной ревизии.

Если harness не умеет запускать подагентов, критика и проверку выполняет отдельный агент в новом контексте. Самопроверка исполнителя не заменяет независимую проверку.

## Источники правды

- Принятые ADR — история и обязательные ограничения решений.
- [design.md](design.md) — актуальное и утверждённое поведение продукта.
- GitHub Issues — все идеи, баги, требования, обсуждения и доказательства проверки.
- Код и тесты — реализация принятых решений.
- [operations.md](operations.md) — запуск, обновление, выпуск и откат.

Открытые идеи не дублируются в Markdown-документах. Закрытые механики остаются в [ideas.md](ideas.md) как историческая справка.

## Жизненный цикл задачи

Рекомендуемые статусы GitHub Projects: `Inbox → Analysis → Ready → In progress → In review → Done`. Релизы отслеживаются через GitHub Releases и при необходимости milestones.

### 1. Предложение

Каждая идея, задача и ошибка начинается с GitHub Issue. Pull Request без связанной задачи допустим только для тривиальной правки вроде опечатки.

Issue содержит:

- проблему или желаемый результат;
- контекст и ограничения;
- для бага — шаги воспроизведения, ожидаемое и фактическое поведение;
- наблюдаемый результат, который докажет завершение работы.

### 2. Анализ

Исполнитель читает затронутые разделы `design.md`, действующие ADR и код. В Issue уточняются причина, объём, ограничения, риски и альтернативы.

`gopnik-critic` проверяет диагноз, значимые обобщения и спорные критерии завершения. Его опорные находки исполнитель проверяет по первичным источникам, а итоговый пересказ возвращает критику на подтверждение. Тривиальные факты и механические правки не требуют критика.

Если меняются продуктовые правила или появляется продуктовый компромисс, решение согласуется с Product Owner до разработки.

### 3. Требования и решение

Issue получает проверяемые критерии приёмки и явный список того, что не входит в работу.

Для значимого изменения сначала создаётся ADR по правилам [реестра](adr/README.md). ADR, затрагивающий продукт, получает статус `accepted` только после согласования Product Owner. Чисто технический ADR принимается через ревью PR; появление продуктовых последствий требует согласования Product Owner.

После принятия ADR и до кода обновляется `design.md`. Для крупной функциональности дополнительно создаётся спецификация с точными правилами, миграциями и критериями приёмки.

Задача готова к разработке (`Ready`), когда:

- критерии приёмки наблюдаемы и проверяемы;
- объём и ограничения понятны;
- нужный ADR принят;
- актуальный дизайн обновлён;
- продуктовые вопросы разрешены Product Owner.

### 4. Подготовка проверки

До реализации исполняемого изменения исполнитель по `gopnik` строит Stage 0 — матрицу поведения из требований Issue, а не из будущего diff. Матрица публикуется комментарием в Issue до начала работы.

Для документации, конфигурации агентов и других неисполняемых изменений Stage 0 не требуется.

### 5. Разработка

Работа ведётся в отдельной ветке от `main`. Прямые push в `main` запрещены.

Исполнитель:

- соблюдает принятые ADR и правила `CLAUDE.md`;
- добавляет тесты, а для бага — регрессионный тест;
- обновляет документацию и инструкции по миграции;
- запускает `.venv/bin/ruff check .` и `.venv/bin/pytest`;
- не расширяет объём без изменения Issue и, при необходимости, ADR.

### 6. Проверка

Изменение оформляется в Pull Request со ссылкой на Issue и затронутые ADR.

Проверка включает:

1. Соответствие критериям приёмки, ADR и `design.md`.
2. Зелёный GitHub Actions: lint, тесты и сборка образа.
3. `gopnik-critic` для диагнозов, объяснений механизмов и других опорных утверждений.
4. `gopnik` для исполняемых изменений: Stage 0, Stage 1 и настроенный Stage 2. Вердикт и доказательства публикуются в Issue.

#### Stage 2: тестовый стенд

Stage 2 настроен в `gopnik.json`: сборка образа, отказ образа без токена и прогон сценария [тестового стенда](operations.md#тестовый-стенд) (`.venv/bin/python -m tools.stand smoke`). Стенд — бот из рабочего дерева на тестовом токене, тестовая группа и новая база. Сценарий подаёт синтетические апдейты, а бот отвечает через настоящий Bot API ([ADR-0015](adr/0015-agent-test-stand.md)).

Агент обязан прогнать стенд и приложить к вердикту `report.public.json`, если изменение затрагивает:

- обработчики команд и кнопок, проверку прав или порядок проверок;
- тексты и разметку сообщений, клавиатуры и `callback_data`;
- вызовы Bot API, меню команд и всё, что бот делает при старте;
- версию aiogram или другую зависимость, через которую идут вызовы Telegram.

Изменение, которое меняет набор команд или их поведение, обновляет сценарий стенда в том же PR. Для правок только в `services/`, `repo/` и контенте без новых текстов стенд не обязателен: хватает Stage 1. Без локального конфига стенда (`.env.stand`) Stage 2 считается недоступным. Вердикт тогда сужается до Stage 1, а причина называется явно.

Ручными остаются проверки, которые требуют человека в клиенте Telegram: privacy mode, команды с суффиксом `@бот`, вид меню и всплывающих ответов, настоящее анонимное сообщение админа и прилёты планировщика. Их перечисляют в PR как ручной смоук для Product Owner.

`READY` относится только к проверенной ревизии и области. Любой `BLOCKER` запрещает merge. Исправление блокера обнуляет прежний вердикт и требует нового полного раунда проверки.

Для документации и конфигурации агентов `gopnik` не нужен; проверяются ссылки, формат файлов, синхронность копий и применимость инструкций.

### 7. Доработка

Доработка возвращает задачу в разработку. Если проблема относится к требованиям или выбранному решению, задача возвращается в анализ.

Нельзя исправить противоречие принятому ADR только кодом. Сначала нужен новый ADR, который переопределяет прежний.

### 8. Финализация

PR можно влить, когда CI зелёный, замечания разрешены, проверки завершены и текущая ревизия не имеет блокеров.

В описании PR используется `Fixes #N`, если merge действительно завершает Issue. После merge Issue закрывается; релизная история ведётся отдельно через GitHub Releases.

Задача считается `Done`, когда изменение влито, документация обновлена и обязательные проверки задокументированы.

## ADR как обязательное ограничение

Принятый ADR нельзя нарушать или переписывать по смыслу. Допустимы только исправления опечаток и ссылок без изменения решения.

Пересмотр оформляется новым ADR:

1. Новый документ ссылается на прежний и объясняет изменившийся контекст.
2. Реализация нового решения начинается после его принятия.
3. Новый ADR получает `Supersedes`, прежний — `Superseded by` и статус `superseded`.
4. `design.md` приводится к новому решению до изменения кода.

Hotfix может восстановить принятое поведение или откатить дефектное изменение. Новое поведение в обход ADR аварийность не разрешает.

## Релизы

Релизы создаются в GitHub из состояния `main`; деплой выполняется отдельно от репозитория.

1. Проверить, что нужные PR влиты, CI на выбранном коммите зелёный, миграции и откат описаны.
2. Выбрать версию по SemVer и тег `vX.Y.Z`.
3. Создать и отправить тег. GitHub Actions повторно проверит код и опубликует Docker-образ в GHCR.
4. Создать GitHub Release для того же тега с изменениями, миграциями, рисками и известными ограничениями.
5. Развернуть неизменяемый образ конкретной ревизии и проверить результат по `operations.md`.
6. При неуспешном обновлении откатить развёртывание; исправление провести через новый Issue и PR.

Релиз не считается завершённым только потому, что тег или образ опубликованы: нужна проверка использования выпущенного артефакта.

## Универсальная конфигурация агентов

- [AGENTS.md](../AGENTS.md) — точка входа для harness, поддерживающих этот стандарт.
- [CLAUDE.md](../CLAUDE.md) — единый текст проектных правил, общий для всех агентов.
- `.agents/skills/` — основная, независимая от harness копия навыков.
- `.claude/skills/` — копия для совместимости с Claude.
- `gopnik.json` — независимая от harness конфигурация проверки.

При обновлении навыка изменяются обе копии. Расхождение `.agents/skills/` и `.claude/skills/` считается ошибкой конфигурации.
