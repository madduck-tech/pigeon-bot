# Спецификация: разнообразие предсказаний и прилётов

Дата: 2026-11-05  
Статус: утверждено  
Основание: [ADR-0001](adr/0001-diversify-pigeon-experience.md)

Документ описывает утверждённые и реализованные правила R1–R3. `docs/design.md` фиксирует текущее поведение; этот документ раскрывает точные правила, миграции и критерии приёмки разнообразия.

## 1. Объём

Входят три последовательно выкатываемых релиза:

1. **R1 — предсказания:** стабильные идентификаторы, новые форматы, колоды без повторов и сохранение выдачи.
2. **R2 — прилёты:** переменные исходы плевка, публичная история действий и игровые типы голубей.
3. **R3 — недельный цикл:** общие задания, недельный рейтинг, итоги и косметические титулы.

Не входят: LLM, новые автоматические сообщения, магазин, дартс, ставки, дуэли, закреплённый дашборд, сериал с опросами, голубиная почта, факты и погода.

## 2. Общие требования

- Состояние каждого чата изолировано. Все новые записи и запросы содержат `chat_id`.
- Всё состояние механик хранится в SQLite и переживает перезапуск.
- Случайность передаётся через существующий `random.Random`; сервисы получают время через clock.
- Изменения баланса выполняются только через `points_ledger`. Старые очки не сбрасываются.
- Новые кнопки и чтение сообщений чата не требуются.
- Лимиты прилётов, тихие часы, пауза и отсутствие пингов сохраняются.
- Тексты остаются в `content/` или `render/`; HTML экранируется в `render/`.
- Результат действия добавляется в существующее сообщение прилёта. Новых сообщений на плевок, прогон или выполнение задания нет.

## 3. R1: предсказания

### 3.1. Формат контента

`content/fortunes.yaml` становится списком объектов:

```yaml
- id: seeds-fall
  format: classic
  text: Сегодня семечки упадут в твою сторону.

- id: gena-saw-bread
  format: scene
  text: "{name} видел булочку на подоконнике. Решил не спрашивать, чья она."

- id: feather-prophecy-1
  format: serial
  part: 1
  next: feather-prophecy-2
  text: Первое перо упало. Голубь сказал, что второе расскажет всё завтра.
```

Правила:

- `id` обязателен, уникален и состоит из строчных латинских букв, цифр и дефисов.
- После публикации идентификаторы не переиспользуются для другого текста.
- `format` — один из `classic`, `omen`, `scene`, `spread`, `chat`, `serial`.
- `text` непустой; многострочный текст разрешён через YAML block scalar.
- Только `scene` может содержать `{name}`. Имя выбирается из `content/names.yaml` при подготовке выдачи.
- `serial` имеет `part`, начиная с 1, и может иметь `next`. Цепочка содержит 2–3 части, не имеет циклов и доступна только общему предсказанию дня.
- Загрузчик отклоняет неизвестные форматы, дубли ID, неверные ссылки `next`, циклы и неподходящие плейсхолдеры при старте.

Начальный набор — **60 записей**:

| Формат | Количество | Назначение |
|---|---:|---|
| `classic` | 30 | Текущие афоризмы с присвоенными ID |
| `omen` | 8 | Конструкция «если…, то…» |
| `scene` | 6 | Короткая сценка с участием случайного голубя |
| `spread` | 6 | Многострочный расклад «Удача / Опасность / Совет» |
| `chat` | 6 | Общее предсказание для участников чата |
| `serial` | 4 | Две цепочки по две части |

### 3.2. Колоды

Константы:

- `FORTUNE_CHAT_EXCLUSION_DAYS = 14`;
- владелец общей колоды в БД — `owner_id = 0`;
- личная колода использует `owner_id = user_id`.

Общая и личные колоды независимы:

- общая содержит все форматы и выдаёт каждый доступный ID один раз за цикл;
- личная содержит все форматы, кроме `serial`;
- внутри новой колоды ID перемешиваются;
- первый ID новой колоды не совпадает с последним ID предыдущей, если доступно больше одного элемента;
- удалённые из контента ID пропускаются, новые ID добавляются в оставшуюся часть колоды в случайных позициях при следующей выдаче.

Личная колода дополнительно не выбирает ID, показанные этому чату в общих или личных предсказаниях за последние 14 локальных дней. Просмотр колоды не удаляет пропущенные из-за этого элемента. Если все оставшиеся элементы заблокированы, личная колода начинает новый цикл досрочно и выбирает из полного набора с тем же ограничением. Поэтому исключение недавних повторов в пределах чата приоритетнее длины личного цикла.

### 3.3. Многочастные пророчества

- Первая часть попадает в общую колоду как обычный элемент.
- При её выдаче остальные части удаляются из остатка колоды и помещаются в персистентную очередь `forced_json` в порядке следования.
- В каждый следующий день общая колода сначала выдаёт очередную часть из `forced_json`.
- Принудительная часть не тратит дополнительный день и не создаёт дополнительный пост.
- Личные предсказания не запускают и не продолжают цепочки.
- При обновлении контента цепочка должна оставаться целой; иначе бот не запускается.

### 3.4. Общее предсказание и повторная отправка

Время публикации определяет существующий `fortune.daily_due()`.

1. В транзакции бот проверяет строку `(chat_id, local_day)` в `daily_fortunes`.
2. Если строки нет, бот выбирает ID, сохраняет `fortune_id`, окончательный `rendered_text`, состояние колоды и `sent_at = NULL`.
3. Если строка с `sent_at = NULL` уже есть, бот использует её сохранённый текст, не продвигая колоду.
4. После успешного ответа Telegram бот записывает `sent_at`.
5. При ошибке отправки строка остаётся неотправленной, и следующий tick повторяет тот же текст.
6. Если ответ Telegram потерян после фактической доставки, возможен дубль того же поста. Это сохраняет текущий компромисс в пользу повторной попытки.
7. Строка с заполненным `sent_at` больше не отправляется.

Метод `release_daily_fortune()` после этого не используется для новой механики.

### 3.5. Личное предсказание

- `/pigeon fortune` сохраняет лимит один раз на участника в локальные сутки.
- Выбор ID, обновление личной колоды и запись `(chat_id, user_id, local_day)` выполняются одной транзакцией.
- Повторная команда в тот же день по-прежнему возвращает `FORTUNE_ALREADY`, а не новый текст.
- Сохраняются `fortune_id` и `rendered_text`, чтобы история не менялась после редактирования YAML.

### 3.6. Отображение

| Формат | Заголовок общего поста |
|---|---|
| `classic` | `🔮 Предсказание дня` |
| `omen` | `🌤 Голубиная примета` |
| `scene` | `🕊 Весть с подоконника` |
| `spread` | `🔮 Расклад от голубя` |
| `chat` | `🏘 Прогноз для района` |
| `serial` | `📜 Пророчество, часть N` |

Личный ответ использует тот же заголовок, но остаётся reply на команду участника. Текст помещается под заголовком; HTML-разметка внутри YAML не поддерживается, переносы строк сохраняются.

## 4. R2: переменный плевок

### 4.1. Исходы обычного голубя

| `outcome` | Диапазон одного `rng.random()` | Шанс | Очки | Успешное попадание |
|---|---|---:|---:|---|
| `normal` | `[0.00; 0.65)` | 65% | +1 | да |
| `miss` | `[0.65; 0.85)` | 20% | 0 | нет |
| `cap` | `[0.85; 0.95)` | 10% | +2 | да |
| `chain` | `[0.95; 1.00)` | 5% | +3 | да |

Математическое ожидание: `0.65×1 + 0.20×0 + 0.10×2 + 0.05×3 = 1` очко за попытку.

После определения исхода реакция выбирается отдельным `rng.choice()` из `content/hits.yaml`. Для каждого исхода должно быть не менее шести реакций; для `cap_knocked` из §5 — не менее четырёх.

### 4.2. Обработка попытки

- Лимит остаётся один `hit` на `(event_id, user_id)`, включая промах.
- Исход, реакция и начисленные очки сохраняются атомарно с попыткой.
- Для положительного результата создаётся запись `points_ledger(reason='hit')`; для нулевого запись не создаётся.
- `Попаданий` — это число успешных исходов `normal`, `cap`, `chain`, а не число попыток и не сумма очков.
- Первый успешный исход передаёт Золотой плевок. `miss` и `cap_knocked` трофей не передают.
- Повторное нажатие после любой попытки возвращает существующий `HIT_ALREADY`.
- Старые записи `hits` считаются `normal` с одним очком.

### 4.3. Публичная история

- В сообщении прилёта показываются последние три действия из объединённой хронологии `hits` и `shoos`.
- Плевок отображается с именем участника, реакцией и очками, например: `💦 Вася: попал в кепку! +2`.
- Промах отображается как `💨 Вася: мимо. Голубь даже не моргнул`.
- Прогон сохраняет текущий формат.
- Под историей остаётся `💦 Попаданий: N`.
- Callback содержит результат, очки и новые ачивки. Он остаётся простым текстом.
- После закрытия прилёта итог содержит число попаданий и спугнувшего, если он есть.

## 5. R2: типы голубей

### 5.1. Правила типов

| `pigeon_type` | Окно | Плевок | Прогон |
|---|---|---|---|
| `normal` | 15 минут | Базовые исходы | Базовые шансы |
| `capped` | 15 минут | Первая попытка в прилёте принудительно имеет исход `cap_knocked`, 0 очков; затем базовые исходы | Базовые шансы |
| `sleepy` | 15 минут | Базовые исходы | +15 процентных пунктов к шансу каждой попытки |
| `golden` | 5 минут | Базовые исходы, очки успешных попаданий ×2 | Базовые шансы |

Дополнительно:

- `cap_knocked` означает сбитую кепку, не засчитывается как попадание и не прерывает общий прилёт.
- Состояние кепки общее на прилёт и хранится в `events.type_state`.
- Для `sleepy` шансы по числу предыдущих попыток: 35%, 50%, 65%, 80%, 95%, 100%; далее 100%.
- Для `golden` множитель применяется к `normal`, `cap` и `chain`: +2, +4, +6. Промах остаётся нулевым.
- Ручной `/pigeon arrive` использует те же типы и правила.
- Старые и открытые во время миграции события получают `normal`.

Тип выводится отдельной строкой сразу после intro, например:

- `🧢 В кепке. Первый плевок только собьёт её.`;
- `💤 Сонный. Прогнать его проще.`;
- `✨ Золотой. Очки ×2, улетит через 5 минут.`.

### 5.2. Колода типов

- На чат ведётся независимая перемешанная колода из 12 элементов: 9 × `normal` и по одному `capped`, `sleepy`, `golden`.
- Каждый новый прилёт, ручной или автоматический, берёт следующий элемент.
- Особый тип не может идти сразу после особого, в том числе на границе циклов. При перемешивании такая последовательность исправляется обменом с `normal`.
- Тип и состояние сохраняются в `events`; после открытия прилёта они не меняются.
- Удалённый или неотправленный прилёт возвращает взятый тип в ту же позицию колоды, чтобы сбой отправки не пропускал контент.

### 5.3. Достижения и статистика

- `sniper` учитывает только успешные попадания в пяти последних прилётах; промах или сбитая кепка вместо попадания прерывают серию.
- `early_bird` учитывает только первые успешные попадания.
- `scarer` работает без изменений, включая `sleepy`.
- `trophy_holder` работает без изменений.
- Рейтинг использует фактический `points_ledger`, поэтому автоматически учитывает критические попадания и золотых голубей.

## 6. R3: недельный цикл

### 6.1. Календарь

- Неделя начинается в понедельник 00:00 по timezone чата.
- `week_key` — ISO-дата понедельника.
- Задание создаётся лениво при первом scheduler pass новой недели.
- Очки недели вычисляются из `points_ledger` между локальными границами недели, преобразованными в UTC.
- Общий баланс и общий рейтинг не обнуляются.

### 6.2. Задания

`content/quests.yaml` содержит стабильные `id`, название, описание, цель и название титула.

Начальная колода:

| `quest_id` | Условие выполнения | Титул |
|---|---|---|
| `trio-hit` | В одном прилёте успешно попали минимум 3 разных участника | Слаженный двор |
| `team-scare` | В одном прилёте попытались прогнать голубя минимум 3 разных участника | Шумный двор |
| `weekly-eight` | За неделю в чате совершено минимум 8 успешных попаданий | Меткий двор |
| `hit-then-scare` | Голубь спугнут после минимум 2 успешных попаданий в этом прилёте | Дворовая стратегия |

Правила:

- Одна колода заданий на чат содержит каждый `quest_id` по одному разу. Новый цикл не начинается с задания, завершавшего предыдущий.
- Прогресс вычисляется из `events`, `hits` и `shoos`, отдельные счётчики не дублируются.
- Выполнение проверяется после каждого плевка и прогона. В БД сохраняются `status=completed` и `completed_event_id`.
- Выполненное задание повторно не завершается. Невыполненное получает `status=failed` при закрытии недели.
- За выполнение не начисляются очки. Чат получает соответствующий постоянный косметический титул.
- Текущее задание и прогресс показываются в сообщении прилёта и `/pigeon stats`.
- Выполнение отмечается строкой в текущем сообщении прилёта без нового поста.

### 6.3. Понедельничный пост

В понедельник существующий слот общего предсказания заменяется сообщением:

1. итог задания прошлой недели и полученный титул, если оно существовало;
2. топ-3 недели, если были очки;
3. новое задание недели.

Ограничения:

- Общая колода предсказаний в этот день не расходуется.
- Сообщение использует `daily_fortunes` и тот же механизм `sent_at`, что обычный ежедневный пост.
- Пауза и тихие часы действуют по текущим правилам. При запуске после понедельника прошедший понедельничный пост не восстанавливается.
- Если чат настроен не в понедельник, задание начинается в текущей неделе, а первый итог появится в следующий понедельник.

### 6.4. Команды и титулы

- `/pigeon stats` по умолчанию показывает топ-10 текущей недели, текущее задание и последний полученный титул.
- `/pigeon stats all` показывает существующий общий топ-10 и держателя Золотого плевка.
- `/pigeon stats week` эквивалентен `/pigeon stats`.
- `/pigeon profile` дополнительно показывает очки текущей недели; общие очки и старые ачивки сохраняются.
- Титулы чата хранятся все, в интерфейсе выводится последний полученный.

## 7. Модель данных и миграции

Имена и точные SQL-миграции могут уточняться при реализации без изменения описанных правил.

### 7.1. Изменения существующих таблиц

```text
fortunes
  + fortune_id TEXT NULL
  + rendered_text TEXT NULL

daily_fortunes
  + fortune_id TEXT NULL
  + rendered_text TEXT NULL
  + sent_at TEXT NULL

hits
  + outcome TEXT NOT NULL DEFAULT 'normal'
  + points INTEGER NOT NULL DEFAULT 1
  + reaction TEXT NOT NULL DEFAULT ''

events
  + pigeon_type TEXT NOT NULL DEFAULT 'normal'
  + type_state TEXT NOT NULL DEFAULT '{}'
```

Старые `daily_fortunes` получают ненулевой `sent_at`, потому что их отправка уже завершилась. Старые `fortunes` остаются с неизвестным `fortune_id`: восстановить прошлый текст невозможно.

### 7.2. Новые таблицы

```text
fortune_decks(
  chat_id, scope, owner_id, cycle,
  remaining_json, forced_json, last_fortune_id,
  PK(chat_id, scope, owner_id)
)

pigeon_type_decks(
  chat_id, remaining_json, last_pigeon_type,
  PK(chat_id)
)

quests(
  chat_id, week_key, quest_id, status, completed_event_id,
  PK(chat_id, week_key)
)

quest_decks(
  chat_id, remaining_json, last_quest_id,
  PK(chat_id)
)

chat_titles(
  id, chat_id, quest_id, title, week_key, awarded_at
)
```

`scope` принимает `daily` или `personal`; для `daily` используется `owner_id=0`. JSON хранится как текст SQLite. Статус задания: `active`, `completed`, `failed`.

### 7.3. Требования к миграции

- Миграции аддитивны, существующая база открывается без удаления данных.
- `points_ledger`, трофеи, достижения и старые события сохраняются.
- До первой новой выдачи невозможно исключить повтор последнего старого предсказания: старый текст не сохранялся. Гарантия начинается с записей, созданных после миграции.
- Открытые во время обновления прилёты остаются `normal` с исходным `closes_at`.
- Идемпотентность проверяется повторным запуском `Store` на одной базе.

## 8. Метрики

Метрики вычисляются из существующих таблиц без чтения сообщений и отдельного сбора переписки:

- **Повтор предсказания:** тот же `fortune_id` у чата за последние 14 локальных дней.
- **Участники прилёта:** число разных `user_id` в объединении `hits` и `shoos`, включая промахи.
- **Доля слабых прилётов:** прилёты с 0–1 участником среди закрытых.
- **Возвращение:** доля участников прилёта N, совершивших действие в следующем прилёте того же чата.
- **Смена трофея:** число записей `trophy_log` и число разных владельцев за период.
- **Задания:** доля завершённых недельных заданий среди чатов, где было хотя бы одно игровое действие.
- **Баланс плевка:** распределение `outcome`, среднее число очков на попытку и доля промахов.

Цель R1 — нулевые повторы `fortune_id` внутри общей колоды и отсутствие личных выдач из 14-дневной истории чата. Для остальных метрик сначала собирается базовый период 2–4 недели; числовые цели устанавливаются после него.

## 9. Критерии приёмки

### R1

- 60 валидных записей шести форматов загружаются при старте.
- Общая колода не повторяет ID до исчерпания; личные колоды разных участников независимы.
- Личная выдача исключает ID из 14-дневной истории чата.
- Обе цепочки выдаются по одной части в последовательные дни.
- Перезапуск не меняет остаток колоды и очередь частей.
- Ошибка отправки общего поста приводит к повтору того же текста без продвижения колоды.
- Чаты и локальные даты изолированы; пауза и тихие часы работают.

### R2

- Границы вероятностей проверены детерминированными тестами; средняя базовая награда равна 1.
- Промах расходует попытку, не даёт очков, попадания, трофея или прогресса `sniper`.
- Первое успешное попадание передаёт трофей; критические очки попадают в ledger.
- Объединённая история показывает три последних действия и корректно экранирует имена.
- `capped`, `sleepy` и `golden` применяют точные правила §5.
- Колода типов не ставит два особых прилёта подряд и переживает перезапуск.
- Старая база сохраняет очки и корректно считает старые попадания.

### R3

- Неделя и границы рейтинга соответствуют timezone чата, включая UTC-offset.
- Каждое задание завершается только при своём условии и только один раз.
- Понедельничный пост заменяет предсказание, не создаёт дополнительный пост и повторяется после ошибки отправки.
- `/pigeon stats`, `week`, `all` и `/pigeon profile` показывают согласованные очки.
- Титулы и состояние заданий переживают перезапуск и не смешиваются между чатами.

### Общее

- Проходят `.venv/bin/ruff check .` и `.venv/bin/pytest`.
- Ручной smoke в тестовом Telegram-чате подтверждает команды, кнопки, редактирование, форматирование и отсутствие новых автоматических сообщений.

## 10. Ограничения эксплуатации

- Контент по-прежнему загружается при старте; для обновления YAML нужен перезапуск.
- Потерянный ответ Telegram может создать дубль ежедневного поста, но не новый элемент колоды.
- При ручных прилётах администратор может ускорить прохождение колод и получение очков; это соответствует существующей возможности ручных прилётов.
- Первые выводы о балансе делаются не раньше 2–4 недель реального использования. Изменение вероятностей после этого не требует нового ADR, если сохраняются принципы ADR-0001; смена механики требует нового ADR.
