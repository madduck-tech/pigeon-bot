# ADR-0011: Выпускать проверенный Docker-образ без CD в репозитории

Дата: 2026-11-06  
Статус: accepted  
Supersedes: —  
Superseded by: —  
Issue / PR: —

## Контекст

Для воспроизводимого запуска нужен артефакт с кодом, зависимостями и контентом, а состояние SQLite должно переживать замену контейнера. Репозиторий проверяет и публикует образ, но не владеет целевой инфраструктурой. Long polling Telegram допускает только один активный опрос с тем же токеном.

Решение зарегистрировано ретроспективно по Dockerfile, CI и процессу эксплуатации.

## Решение

- Приложение поставляется как Docker-образ на Python 3.12. Зависимости, пакет и YAML-контент включаются в образ; процесс запускается от непривилегированного пользователя.
- База находится в `/data/pigeon.db` на постоянном томе. Контейнер без такого тома не считается сохраняющим состояние развёртыванием.
- GitHub Actions сначала запускает `ruff check` и `pytest`, затем собирает образ. Для pull request образ проверяется без публикации; для `main` и тегов `v*` публикация идёт в GHCR.
- Релиз получает SemVer-тег `vX.Y.Z`, GitHub Release и образ конкретной ревизии. Для развёртывания предпочтителен неизменяемый SHA- или версионный тег, а не подвижный тег ветки.
- Репозиторий заканчивается публикацией артефакта. CD и манифесты конкретной инфраструктуры в него не входят; развёртывание и проверка работающего выпуска выполняются отдельно.
- С одним токеном запускается один активный экземпляр long polling. Второй экземпляр с тем же токеном не является способом масштабирования и приводит к конфликту опроса.
- Перед обновлением с миграциями делается копия SQLite. Откат образа не откатывает уже изменённую схему или данные; для этого нужна совместимая схема либо восстановление из копии по описанной процедуре.
- Публикация образа сама по себе не завершает релиз: нужно развернуть конкретную ревизию и проверить использование выпущенного артефакта.

## Последствия

### Положительные

- Одна и та же ревизия проходит проверки и становится воспроизводимым артефактом.
- Код и контент обновляются вместе, а база сохраняется отдельно от контейнера.
- Инфраструктура и секреты развёртывания не связываются с репозиторием бота.

### Отрицательные и ограничения

- Выкатка и наблюдение за ней не автоматизированы этим репозиторием и требуют внешней процедуры.
- Одна реплика и long polling не дают горизонтального масштабирования или бесшовного переключения двух экземпляров с одним токеном.
- Откат приложения после необратимой миграции данных требует заранее сделанной копии и явного решения о восстановлении.

## Рассмотренные альтернативы

- **Запуск напрямую из исходников на сервере.** Отклонён как основной выпуск: среда и зависимости менее воспроизводимы.
- **Автоматический CD из этого репозитория.** Отклонён: целевая инфраструктура управляется отдельно, а публикация образа не доказывает готовность работающего бота.
- **Развёртывание только по подвижному тегу ветки.** Отклонено: затрудняет доказательство ревизии и точный откат.
- **SQLite внутри replaceable container filesystem.** Отклонено: состояние теряется при замене контейнера.
