# ADR-0015: Тестовый стенд в Telegram с синтетическими апдейтами

Дата: 2026-11-08  
Статус: accepted  
Supersedes: —  
Superseded by: —  
Issue / PR: [#22](https://github.com/madduck-tech/pigeon-bot/issues/22), принят ревью [PR #24](https://github.com/madduck-tech/pigeon-bot/pull/24) 2026-11-08

## Контекст

Агенты проверяют изменения на Stage 1 (`ruff`, `pytest` с поддельной сессией aiogram). Stage 2 в `gopnik.json` проверял только сборку образа и `getMe`. Принимает ли Telegram разметку и кнопки, как работает `getChatMember` для участника и админа, что лежит в меню команд, человек проверял руками (пример — ручной смоук PR #21).

Ограничения Bot API и решения Product Owner (2026-11-08, Issue #22):

- Бот в группе не получает сообщения других ботов, поэтому второй бот не может управлять нашим.
- Управление с пользовательского аккаунта через MTProto отклонено.
- Через Bot API нельзя прочитать историю группы, поэтому доказательства должен собирать сам харнес.
- Ответ на `callback_query`, которого Telegram не отправлял, отклоняется: `query ID is invalid`.

Действующие ограничения: слоистость и инжектируемое время ([ADR-0005](0005-layered-monolith-sqlite.md)), один long polling на токен ([ADR-0011](0011-container-release-without-cd.md)), приватность ([ADR-0004](0004-privacy-and-minimal-data.md)), HTML-разметка ([ADR-0010](0010-html-rendering-and-escaping.md)).

## Решение

- Харнес живёт в `tools/stand/`, вне `src/pigeon/`. Прод-код ради стенда не меняется. Харнес собирает бота так же, как `pigeon.app.run_bot`: `build_bot`, `Store`, `load_content`, `build_router`, `SystemClock`. Long polling и планировщик на стенде не запускаются.
- Сценарий подаёт синтетические `Update` (команды и `callback_query`) в `Dispatcher.feed_update`. Исходящие вызовы идут в настоящий Bot API, бот действительно постит в тестовую группу.
- Перехват делает request-middleware сессии aiogram (`bot.session.middleware`). Это публичная точка расширения aiogram, а не подмена прод-кода. Middleware пишет в отчёт каждый вызов: метод, параметры, ответ Telegram или ошибку.
- Синтетические отправители — реальные участники тестовой группы, поэтому права проверяет настоящий `getChatMember`:
  - **админ** — аккаунт владельца стенда;
  - **участник** — дополнительный бот без прав админа;
  - **анонимный админ** — апдейт с `sender_chat`, равным тестовой группе.
- Ошибка `answerCallbackQuery` для синтетического `callback_query` с текстом «query is too old» или «query ID is invalid» считается ожидаемой. Харнес помечает её в отчёте `expected_error`, и обработчик продолжает работу, как после успешного ответа. Любая другая ошибка Telegram валит сценарий.
- Защита:
  - Первый вызов — `getMe`. Если это прод-бот `golubinskity_bot`, харнес отказывается работать. До этой проверки middleware блокирует все остальные методы.
  - Каждый прогон получает новую папку с уникальным суффиксом и новую базу SQLite в ней. `PIGEON_DB_PATH` харнес не читает.
  - Отчёт фиксирует ревизию дерева, из которого импортирован код бота. Если это не дерево харнеса, прогон проваливается.
  - Middleware блокирует любой вызов с `chat_id`, отличным от `chat_id` стенда.
  - Токен не попадает ни в логи, ни в отчёт: перед записью отчёт проверяется на вхождение токена.
- Данные стенда (токен, `chat_id`, `user_id` админа и участника) лежат только локально: в git-ignored файле `.env.stand` или в переменных окружения `PIGEON_STAND_*`. В репозитории — `.env.stand.example` с плейсхолдерами. Без конфига харнес завершается с кодом 2 и перечисляет недостающие переменные.
- Отчёт — JSON в `stand-runs/<время>-<сценарий>/report.json` (git-ignored): ревизия, бот, поданные апдейты, вызовы Bot API с ответами, проверки и итог. Рядом лежит `report.public.json`, где идентификаторы стенда заменены плейсхолдерами: его можно публиковать в Issue.
- Сценарии — Python-модули в `tools/stand/scenarios/`. Ожидаемые тексты берутся из `pigeon.render.texts`, а не дублируются. Запуск: `.venv/bin/python -m tools.stand <сценарий>`. Код выхода: 0 — прошёл, 1 — проверка не прошла, 2 — конфиг или защита.
- Обычный `pytest` и CI стенд не запускают и в сеть не ходят. Логику харнеса проверяют офлайн-тесты в `tests/stand/` с поддельной сессией.
- Stage 2 в `gopnik.json` вызывает сценарий стенда. `docs/development-flow.md` определяет, когда агент обязан прогонять стенд.

Не входит: MTProto и проверка доставки команд от человека (privacy mode, суффикс `@бот`, вид меню в клиенте), запуск стенда в CI, автоматическое создание бота и группы, прогон планировщика.

## Последствия

### Положительные

- Агент сам проверяет на настоящем Telegram разметку, кнопки, редактирование сообщений, `getChatMember` и меню команд и получает машиночитаемое доказательство по конкретной ревизии.
- Стенд не опрашивает обновления, поэтому не конфликтует с другим экземпляром на том же токене.
- Любой разработчик поднимает свой стенд по документации, не трогая чужие данные.

### Отрицательные и ограничения

- Харнес повторяет сборку из `run_bot`. Если `run_bot` начнёт регистрировать что-то ещё (роутер, middleware, вызов при старте), харнес нужно обновить вместе с ним. Шаги вроде публикации меню сценарий вызывает явно.
- Синтетический апдейт обходит доставку Telegram: privacy mode, суффикс `@бот`, анонимность админа и вид клиента проверяет человек.
- `answerCallbackQuery` на стенде всегда отклоняется, поэтому вид всплывающего ответа виден только в параметрах вызова, а не в клиенте.
- Входящие сообщения синтетические и в группе их нет. `message.reply` на такой `message_id` Telegram отклонит, поэтому такие ответы на стенде проверяются только с этой оговоркой.
- Прогон оставляет в тестовой группе сообщения бота. Это шум стенда, а не прода.
- Сценарий зависит от набора команд текущей ревизии: при смене команд сценарии меняются в том же PR.
- Меню команд принадлежит тестовому боту целиком. Сценарий, который его проверяет, сначала сбрасывает меню, поэтому два таких прогона с одним токеном одновременно не запускаются.

## Рассмотренные альтернативы

- **Пользовательский аккаунт через MTProto.** Проверил бы доставку как у человека, но требует сессии живого аккаунта и отклонён Product Owner.
- **Второй бот, который пишет команды в группу.** Не работает: бот не получает сообщения других ботов.
- **Long polling на стенде и ручные действия человека.** Это текущий ручной смоук, от которого и уходим.
- **Полностью поддельный Telegram.** Уже есть на Stage 1 и не проверяет, что Telegram принимает разметку, кнопки и права.
- **Подмена сессии через изменение `pigeon.app`.** Потребовала бы точку расширения в прод-коде; публичного middleware aiogram достаточно.
