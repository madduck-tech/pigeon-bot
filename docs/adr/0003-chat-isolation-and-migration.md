# ADR-0003: Изолировать состояние чатов и переносить `chat_id` без слияния

Дата: 2026-11-06  
Статус: accepted  
Supersedes: —  
Superseded by: [ADR-0018](0018-usage-statistics.md) частично (перенос аналитики без настройки)
Issue / PR: —

## Контекст

Бот работает одновременно в нескольких групповых чатах, но игра является локальной для каждого сообщества. При миграции группы в супергруппу Telegram меняет `chat_id`: состояние нужно перенести, не смешав два независимо настроенных чата.

Решение зарегистрировано ретроспективно по действующему дизайну и реализации.

## Решение

- Вся игровая и настроечная информация принадлежит конкретному `chat_id`; глобального состояния чатов внутри процесса и общего рейтинга между чатами нет.
- Участник идентифицируется парой `(chat_id, user_id)`. Очки, достижения, трофеи, колоды, задания, лимиты и расписание разных чатов не смешиваются.
- Чатовые таблицы содержат `chat_id`, а чатовые выборки ограничиваются им. Внутренние чтение или изменение по первичному ключу события допускаются только на границе, которая проверила принадлежность события текущему чату; `game.live_event()` выполняет такую проверку для действий с прилётом.
- До явной настройки чат не участвует в автоматических публикациях. Команды настройки описаны в ADR-0008.
- При миграции в супергруппу обрабатываются оба направления служебного update и ошибка Telegram с новым `chat_id` как запасной путь.
- Если новый идентификатор ещё не настроен, `chat_id` обновляется во всех таблицах, которые его содержат. Список таблиц определяется по схеме SQLite, чтобы новая таблица не была забыта.
- Если новый чат уже настроен, данные двух чатов не объединяются: старый идентификатор отключается, его записи остаются в базе, а повторные публикации на него прекращаются.
- Повторное уведомление о той же миграции идемпотентно: при отсутствии исходного чата перенос не выполняется.

## Последствия

### Положительные

- Один чат не может изменить рейтинг, расписание или игровое состояние другого через штатные сценарии.
- Миграция в супергруппу сохраняет историю и настройки без ручного восстановления.
- Запрет слияния исключает неоднозначное объединение рейтингов, трофеев и открытых событий.

### Отрицательные и ограничения

- Изоляцию необходимо проверять для каждой новой таблицы, выборки и границы вызова; наличие `chat_id` в схеме само по себе не доказывает безопасность произвольного запроса по ID.
- При коллизии идентификаторов старый чат остаётся отключённым до отдельного ручного решения; автоматического слияния нет.
- Перенос по всем таблицам должен учитывать ограничения уникальности и выполняться транзакционно.

## Рассмотренные альтернативы

- **Общий рейтинг всех чатов.** Отклонён: противоречит локальной игре сообщества.
- **Начинать пустую базу после смены `chat_id`.** Отклонено: теряет историю и настройки существующего чата.
- **Автоматически объединять два настроенных чата.** Отклонено: не существует однозначных правил для конфликтующих участников, трофеев, событий и колод.
- **Перечислять переносимые таблицы вручную.** Отклонено: новую таблицу легко пропустить; список выводится из схемы.
