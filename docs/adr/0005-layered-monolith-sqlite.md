# ADR-0005: Слоистый монолит с долговременным состоянием в SQLite

Статус: accepted  
Supersedes: —  
Superseded by: —

## Контекст

Для небольшого Telegram-бота нужны простое развёртывание, переживающее перезапуск состояние и детерминированные тесты. Внешняя база данных, отдельные воркеры и тяжёлые ORM добавили бы эксплуатационные зависимости без соответствующей нагрузки. При этом Telegram-специфика не должна проникать в правила игры.

Решение зарегистрировано ретроспективно по действующей архитектуре.

## Решение

- Приложение — один Python 3.12-процесс с aiogram 3 long polling и встроенным scheduler-циклом. Tick выполняется каждые 30 секунд; прилёты и ежедневные публикации обрабатываются отдельными проходами, чтобы сбой одного не отменял другой.
- Ответственность разделена по слоям: `handlers/` принимает апдейты, `services/` содержит правила, `repo/` работает с хранилищем, `scheduler/` выполняет плановые проходы, `budget/` ограничивает автопубликации, `render/` собирает тексты, `telegram/` адаптирует aiogram.
- `services/` не импортирует aiogram. Отправка и редактирование сообщений проходят через Telegram-адаптер и протоколы отправителей.
- SQLite через `sqlite3` является единым долговременным хранилищем. События, действия, планы, колоды и незавершённые публикации сохраняются до перезапуска процесса.
- Составные изменения состояния выполняются транзакционно. Баланс вычисляется из `points_ledger`; прямое изменение отдельного поля баланса не используется.
- Временные метки хранятся как timezone-aware UTC. Локальные день, неделя и окна публикаций вычисляются из часового пояса чата.
- Время передаётся через `Clock`, случайность — через `random.Random`. Сервисы не обращаются к системным часам напрямую.
- Изменения схемы выполняются при старте аддитивными идемпотентными миграциями. Текущие обновления сохраняют существующий ledger, события, трофеи и достижения; очистка рейтинга при первоначальном переходе к Голубятне не является повторяемой процедурой обновления.
- Тесты сервисов работают без Telegram, репозитории проверяются на временной SQLite, а Telegram-маршрутизация — с фейковой сессией.

## Последствия

### Положительные

- Перезапуск не теряет открытые прилёты, очередь контента и планы публикаций.
- Правила можно проверять с фиксированными временем и случайностью без реальных задержек и сети.
- Для эксплуатации нужны только процесс бота и постоянный файл базы.

### Отрицательные и ограничения

- Одна SQLite-база и встроенный scheduler рассчитаны на один активный экземпляр с одним токеном, а не на горизонтальное масштабирование.
- Миграции через `ALTER TABLE` и ручной SQL требуют тестов на старых схемах и резервной копии перед обновлением.
- Слои поддерживаются соглашениями и тестами; обход их ради быстрого доступа к Bot API запрещён.

## Рассмотренные альтернативы

- **Внешняя СУБД и ORM.** Отклонены для текущей нагрузки: увеличивают число зависимостей и стоимость эксплуатации.
- **Отдельный scheduler или внешний cron.** Отклонены: добавляют координацию процессов, тогда как встроенный цикл использует то же хранилище и адаптер.
- **Состояние только в памяти.** Отклонено: перезапуск терял бы прилёты, лимиты, колоды и повторные отправки.
- **Прямые вызовы aiogram из сервисов.** Отклонены: связывали бы игровые правила с Telegram и усложняли тестирование.
