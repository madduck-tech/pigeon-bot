# ADR-0010: Централизовать HTML-разметку и экранирование вставок

Дата: 2026-11-06  
Статус: accepted  
Supersedes: —  
Superseded by: —  
Issue / PR: —

## Контекст

Сообщения содержат имена участников и редакторский YAML-контент. В Telegram Markdown спецсимволы в таких вставках могут ломать отправку; HTML требует последовательного экранирования `<`, `>` и `&`. Разбросанная по механикам разметка усложняет проверку этого инварианта.

Решение зарегистрировано ретроспективно по действующему представлению сообщений.

## Решение

- Все сообщения Bot отправляются с глобальным `parse_mode=HTML`; Markdown для пользовательских сообщений не используется.
- `render/` отвечает за заголовки, выделение, сборку сообщений и экранирование вставок. Имена участников, имена голубей, YAML-тексты и другие динамические значения нельзя вставлять в HTML без экранирования.
- HTML внутри YAML не поддерживается: контент рассматривается как текст, а не как доверенная разметка.
- Всплывающие ответы на callback остаются простым текстом и не используют HTML-разметку.
- Отправка и редактирование прилётов и автоматических постов выполняются через общие Telegram-помощники; обработчики команд могут отвечать через `answer()` и `reply()` напрямую, но используют тексты из `render/`. Ошибка `message is not modified` при повторном редактировании игнорируется, остальные ошибки не скрываются.
- Имена выводятся текстом без mention-сущностей по ADR-0004.
- Текущее исключение: `services/weekly.py` сам собирает HTML для задания и понедельничного итога, используя экранирование из `render/texts.py`. Это известное отклонение от целевой границы слоёв, а не образец для новых механик; новые представления следует размещать в `render/` либо отдельно пересматривать границу.

## Последствия

### Положительные

- Спецсимволы в именах и контенте не получают управляющего смысла в разметке.
- Изменение представления не требует менять вероятности, расписание и хранение.
- Повторное редактирование одинакового текста не превращается в ложный сбой механики.

### Отрицательные и ограничения

- Каждая новая вставка требует проверки экранирования, включая многострочный контент и итоговые сообщения.
- Исключение в `weekly.py` означает, что текущая структура ещё не полностью соответствует правилу централизации; перенос представления остаётся техническим долгом.
- HTML не решает ограничения Telegram на длину сообщения и частоту редактирования.

## Рассмотренные альтернативы

- **Markdown или MarkdownV2.** Отклонены: больше спецсимволов в пользовательских именах и контенте требуют защиты.
- **Доверенный HTML в YAML.** Отклонён: редакторский контент получал бы контроль над разметкой сообщений.
- **Экранирование в местах получения данных.** Отклонено: данные должны оставаться исходным текстом, а правило представления — находиться у границы сообщения.
