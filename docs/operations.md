# Эксплуатация

Как запустить, настроить и обновить бота. Устройство бота и решения описаны в [design.md](design.md).

## Боты

| Бот | Для чего |
|---|---|
| [@golubinskity_bot](https://t.me/golubinskity_bot) | Основной бот, «Дерзкая голубятня» |
| Свой тестовый бот | Разработка и [тестовый стенд](#тестовый-стенд). У каждого разработчика свой; имя и токен хранятся только локально |

С одним токеном может работать только один экземпляр: второй получит от Telegram конфликт при опросе обновлений.

## Настройка в BotFather

- Имя: `Дерзкая голубятня`.
- Аватар: `assets/avatar.png`.
- Команда `/setprivacy` → `Enable`. Боту не нужно читать сообщения чата, ему хватает команд и кнопок.

Бот-админ получает все сообщения независимо от этой настройки, поэтому права админа ему лучше не выдавать. Перед тем как их снять, проверьте, что `/pigeon setup` всё ещё узнаёт админов чата: Telegram гарантирует `getChatMember` только боту-админу.

## Настройки окружения

| Переменная | Значение | По умолчанию |
|---|---|---|
| `PIGEON_BOT_TOKEN` | Токен бота | обязательна |
| `PIGEON_DB_PATH` | Путь к базе SQLite | `./data/pigeon.db`, в образе `/data/pigeon.db` |
| `PIGEON_CONTENT_DIR` | Папка с YAML-контентом | `./content`, в образе `/app/content` |
| `PIGEON_LOG_LEVEL` | Уровень логов | `INFO` |

Настройки можно положить в файл `.env` в корне проекта. Он не попадает в git и в образ.

## Запуск в Docker

База лежит в томе `/data`. Без постоянного тома она пропадёт вместе с контейнером.

```sh
docker build -t pigeon-bot:local .
docker run -d --name pigeon --env-file .env -v pigeon-data:/data \
  --restart unless-stopped pigeon-bot:local
```

Логи: `docker logs -f pigeon`.

## Тестовый стенд

Стенд прогоняет сценарий против настоящего Bot API без участия человека. Харнес (`tools/stand/`) собирает бота из рабочего дерева на тестовом токене и подаёт в диспетчер синтетические апдейты: команды и нажатия кнопок. Ответы бота уходят в настоящую тестовую группу. Long polling и планировщик не запускаются, поэтому стенд не конфликтует с другим экземпляром на том же токене. Решение и ограничения — [ADR-0015](adr/0015-agent-test-stand.md).

Права проверяются по-настоящему: бот вызывает `getChatMember` в тестовой группе. Поэтому синтетические отправители — реальные участники группы:

- **админ** — ваш аккаунт;
- **участник** — второй бот без прав админа. Бот не может писать другому боту, но у него есть `user_id`, и `getChatMember` для него работает;
- **анонимный админ** — апдейт с `sender_chat`, равным группе. Отдельный аккаунт не нужен.

### Что создать

1. **Тестовый бот.** В [@BotFather](https://t.me/BotFather) создайте бота и включите `/setprivacy` → `Enable`, как у основного. Токен основного бота использовать нельзя: харнес откажется работать, если `getMe` вернёт `golubinskity_bot`.
2. **Бот-участник.** Создайте второго бота или возьмите любого своего. Его токен стенду не нужен.
3. **Группа.** Создайте группу, добавьте тестового бота, затем бота-участника. Бота-участника добавляйте обычным участником, без прав админа. Права админа тестовому боту не обязательны.

### Как узнать идентификаторы

Нужны `chat_id` группы, ваш `user_id` и `user_id` бота-участника. Их можно получить у Bot API тестового бота. Пока вы это делаете, никакой другой процесс не должен опрашивать обновления с этим токеном: `getUpdates` с ним конфликтует.

1. Добавьте бота-участника в группу после тестового бота, а затем напишите в группе команду с суффиксом, например `/pigeon@<имя_тестового_бота>`. С privacy mode бот получает такие команды и сервисные сообщения о новых участниках.
2. Откройте `https://api.telegram.org/bot<токен>/getUpdates` в браузере. Ссылку никому не пересылайте: в ней токен.
   - `chat_id` группы — `message.chat.id`, у супергруппы он начинается с `-100`.
   - Ваш `user_id` — `message.from.id` вашей команды.
   - `user_id` бота-участника — `id` в `message.new_chat_members` сервисного сообщения о его вступлении.
3. Проверьте себя: `getChatAdministrators?chat_id=<chat_id>` должен показать вас, а `getChatMember?chat_id=<chat_id>&user_id=<id участника>` — статус `member`.

Если группа станет супергруппой, `chat_id` изменится. Тогда возьмите новый из `getUpdates`.

### Локальный конфиг

```sh
cp .env.stand.example .env.stand
```

Заполните `PIGEON_STAND_TOKEN`, `PIGEON_STAND_CHAT_ID`, `PIGEON_STAND_ADMIN_ID` и `PIGEON_STAND_MEMBER_ID`. Файл `.env.stand` в `.gitignore`. Харнес ищет его в текущей папке. Из другого worktree укажите путь явно: `--env-file /путь/к/основному/репо/.env.stand`. Переменные окружения с теми же именами перекрывают файл. Без конфига харнес завершается с кодом 2 и перечисляет, чего не хватает. `PIGEON_DB_PATH` стенд не читает: каждый прогон получает новую базу в своей папке.

### Запуск

```sh
.venv/bin/python -m tools.stand smoke     # команды /pigeon <sub> текущего main
.venv/bin/python -m tools.stand commands  # отдельные команды и меню ADR-0013 (PR #21)
```

Код выхода: `0` — сценарий прошёл, `1` — проверка не прошла, `2` — стенд отказался работать: нет конфига, прод-бот, бот не в группе или нет сети. Каждый прогон постит в тестовую группу несколько сообщений. Бюджет шума и тихие часы работают как в проде, и сценарий может менять их командами.

Сценарий `smoke`:

1. `/pigeon setup Europe/Moscow` от админа.
2. `/pigeon stats` и `/pigeon` от участника.
3. `/pigeon arrive` от участника: бот должен отказать.
4. `/pigeon arrive` от админа.
5. Плевок участника по настоящему сообщению прилёта.
6. `/pigeon quiet 23 8` от анонимного админа.
7. `getMyCommands` для двух скоупов групп. На main бот меню не публикует, поэтому результат только записывается в отчёт.

Сценарий `commands` проходит тот же путь с командами `/setup`, `/stats`, `/pigeon stats`, `/arrive` и `/quiet`. Перед этим он сбрасывает меню обоих скоупов (`deleteMyCommands`), чтобы меню от прошлого прогона не скрыло поломку, и публикует меню, как `run_bot` при старте. В конце он сверяет `getMyCommands` обоих скоупов с меню ревизии. Без `pigeon.telegram.commands` он сразу падает. Меню общее для всего тестового бота, поэтому два прогона `commands` с одним токеном одновременно не запускайте.

### Отчёт

Харнес пишет каждый прогон в новую папку `stand-runs/<время>-<сценарий>-<суффикс>/`. Два прогона, начатые в одну секунду, не делят папку и базу. Папка `stand-runs/` в `.gitignore`.

- `report.json` — полный отчёт. В нём ревизия (`commit` и `dirty`), бот, поданные апдейты, вызовы Bot API с параметрами и ответами Telegram, проверки шагов и общие проверки. Токена в отчёте нет: перед записью харнес проверяет его вхождение.
- `report.public.json` — тот же отчёт, но идентификаторы, имена и пути стенда заменены плейсхолдерами. Его можно приложить к Issue.
- `stand.db` — база прогона.

Как читать отчёт:

- `passed` — итог прогона, `summary.failed_steps` — упавшие шаги.
- `revision` — коммит и `dirty` дерева, из которого импортирован код бота. `same_tree_as_harness: false` значит, что `pigeon` взят из другого рабочего дерева (общий `.venv`), и прогон считается проваленным.
- `steps[].update` — что подано боту, а `actor` — от чьего имени.
- `steps[].calls[]` — что бот отправил в Telegram и что тот ответил: `ok`, `result` или `error`.
- `expected_error` у `answerCallbackQuery` — норма. Telegram не знает id синтетического `callback_query` и отклоняет ответ. Текст всплывающего ответа виден в `params.text`.
- `flood_waits` — сколько секунд харнес ждал по `retry_after`, когда Telegram включил flood control в группе стенда. После ожидания вызов отправляется заново, но не больше трёх раз и не дольше 60 секунд за раз. Частые прогоны подряд упираются в лимит сообщений группы, это не дефект бота.
- `blocked` — вызов, который харнес не пустил в Telegram: до проверки `getMe` или в чужой `chat_id`. Такой вызов валит прогон.

### Что остаётся ручным

Синтетический апдейт обходит доставку Telegram. Человек по-прежнему проверяет privacy mode, команды с суффиксом `@бот`, вид меню и всплывающих ответов в клиенте, а также настоящее анонимное сообщение админа. Планировщик стенд не запускает.

## Публикация образа

CI (`.github/workflows/docker.yml`) запускает `ruff` и `pytest`, затем собирает образ. При пуше в `main` и тегов `v*` образ публикуется в `ghcr.io/madduck-tech/pigeon-bot`. Выкатка делается вне этого репозитория.

## Выпуск релиза

1. Убедиться, что нужные PR влиты в `main`, CI выбранного коммита зелёный, а миграции и способ отката описаны.
2. Выбрать версию по SemVer, создать аннотированный тег и отправить его:

   ```sh
   git tag -a vX.Y.Z <commit> -m "vX.Y.Z"
   git push origin vX.Y.Z
   ```

3. Дождаться успешного GitHub Actions и публикации образа с тегом версии.
4. Создать GitHub Release для того же тега. В заметках перечислить изменения, миграции, риски и известные ограничения.
5. Развернуть неизменяемый образ конкретной ревизии и проверить его использование. Публикация образа без этой проверки не означает завершённый релиз.
6. При неуспехе откатить развёртывание на предыдущий образ. Исправление оформить новым Issue, PR и релизом.

Общий цикл и обязательные проверки описаны в [development-flow.md](development-flow.md).

## Переход со старой версии

Старый бот с дартсом, дуэлями и дашбордом обновляется на месте. Миграции меняют схему и данные, поэтому откат образа сам по себе базу не восстанавливает.

1. Сделайте копию базы.
2. Запустите новую версию. Текущие миграции сохраняют `points_ledger`, трофей, ачивки и историю прилётов; старые `username` участников стираются, потому что они больше не нужны. Таблицы закрытых механик не удаляются, код их просто не читает. Для подарков 18+ добавляется `chats.adult_enabled=0`: режим остаётся выключен во всех существующих чатах, а цель и выдача подарка хранятся в `events.type_state`.
3. Вручную открепите старый дашборд и закройте опросы за имя, если они остались открытыми: бот их больше не трогает.

Старая версия полностью сохранена в git-теге `pre-dovecote`.
